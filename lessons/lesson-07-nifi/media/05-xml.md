# XML, XPath и XSLT

## Структура XML
- Узел имеет имя и пространство имён
- Атрибуты и дочерние элементы читаются по-разному
- Повторяющиеся элементы образуют последовательность
```xml
<Order xmlns="urn:lab:orders">
  <Id>o-101</Id>
  <Customer id="c-1"/>
</Order>
```
> У нас есть документ заказа с корневым элементом ордер, полем ай ди и клиентом. Идентификатор клиента записан в атрибуте. Элементы ордер, ай ди и кастомер принадлежат пространству имён, указанному в атрибуте икс эм эл эн эс. Два элемента могут выглядеть одинаково по локальному имени и относиться к разным схемам. Для корректного чтения нужно знать полное имя. Следом проверим, почему простой путь, который буквально повторяет имена из документа, не возвращает результат.

## XPath и default namespace
- Префикс o связывается с urn:lab:orders
- Абсолютный путь начинается с корня
- Customer/@id обращается к атрибуту
```xpath
/o:Order/o:Id
/o:Order/o:Customer/@id
count(/o:Order/o:Lines/o:Line)
```
> В XPath первой версии имя без префикса выбирает элемент без пространства имён. Наш ай ди в пространстве заказов, поэтому выражение должно использовать префикс, заранее связанный с этим адресом. В XSLT это делается объявлением на элементе стайлшит. Префикс в запросе может отличаться от префикса исходного документа. Важен адрес пространства имён. Обычный атрибут ай ди без префикса при этом остаётся без пространства имён. Проверьте пути к полю заказа, атрибуту клиента и количеству строк.

## Чтение XSLT
- template match выбирает контекст входа
- for-each проходит по позициям
- Attribute value template вычисляет значение
```xml
<xsl:template match="/o:Order">
  <normalized-order id="{o:Id}">
    <!-- Вложенные шаблоны и элементы -->
  </normalized-order>
</xsl:template>
```
> XPath отвечает за выбор узлов. XSLT описывает структуру выходного результата. Шаблон в готовой форме выбирает корневой заказ, создаёт элемент нормалайзд ордер и подставляет идентификатор. Затем цикл проходит по строкам. Внутри цикла текущим узлом становится позиция, поэтому SKU читается как атрибут текущей строки. Когда шаблон не совпадает, могут сработать встроенные правила и выдать незапланированный результат. Проверяйте выходной контракт, включая имя корня и число элементов, даже когда сам процессор не сообщил об ошибке.

## SOAP и входные ограничения
- SOAP Envelope содержит Body, иногда Fault
- Transport status и бизнес-ошибка проверяются отдельно
- Внешние XML ресурсы и большие документы требуют ограничений
> SOAP добавляет конверт и тело сообщения вокруг бизнес документа. Ответ может содержать специальный элемент фолт. Наш мок умеет показать его и при серверной ошибке, и при статусе двести. Поэтому посмотрите одновременно на статус и структуру тела. Перед обработкой документов от партнёра согласуйте размер, глубину, схему и политику внешних ресурсов. Защищённая настройка процессора помогает ограничить обработку, но поведение конкретного парсера проверяют отдельно на используемой версии. Ошибка валидации должна оставить понятный след, по которому можно найти исходную отправку.
