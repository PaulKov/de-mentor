# Groovy и жизненный цикл FlowFile

## Граница скрипта
- Готовые процессоры закрывают стандартный ввод и вывод
- Скрипт выражает небольшое правило предметной области
- Контракт скрипта включает success и failure
> Груви удобен, когда требуется компактное правило, которое трудно выразить конфигурацией. В нашем примере надо разобрать JSON объекта, проверить тип и непустое значение идентификатора, убрать пробелы и записать нормализованный документ. Эту логику можно проверить на нескольких входах. Подключение к базе, чтение из брокера и стандартные повторные попытки лучше оставить специализированным процессорам. Это уменьшает объём кода в скрипте и сохраняет видимость работы на полотне. Практику начнём с успешно обработанного заказа, затем проверим ветку ошибки.

## ProcessSession и StreamCallback
- session.get получает FlowFile из очереди
- session.write меняет content
- После изменения сохраняется возвращённая ссылка
```groovy
def ff = session.get()
if (!ff) return
ff = session.write(ff, callback)
session.transfer(ff, REL_SUCCESS)
```
> В начале запуска процессор получает флоу файл из сессии. Очередь может оказаться пустой, особенно при параллельной работе, поэтому проверяем результат. Колбэк получает поток входных байтов и поток для результата. После записи сохраняем ссылку, которую вернул вызов. То же правило применяем при изменении атрибутов. Далее передаём обработанный файл по именованной ветке. Корректно завершённая сессия фиксирует изменения на стороне Найфай. Внешний запрос, сделанный внутри скрипта, потребует отдельной модели отказа.

## Пример нормализации идентификатора
- Тип event_id проверяется до trim
- Пробелы удаляются вокруг строки
- Код ошибки доступен в атрибутах
> Посмотрите скрипт normalize точка groovy. Парсер превращает JSON в объект. Затем проверяем, что вход представляет объект с непустым строковым идентификатором. Идентификатор с пробелами корректируется, а нулевое значение и число отправляются в ветку ошибки. Назначьте код, который оператор сможет группировать в метриках, и не копируйте исходное тело в сообщение лога. Для практики поменяйте вход с валидной строки на пустую. Проверьте, что получился файл в каталоге ошибок и атрибут причины виден в провенанс.

## Память, многопоточность и ошибки
- JsonSlurper строит объект в памяти
- Несколько задач повышают пиковое потребление
- Постоянный сбой и повреждённые данные требуют разных действий
> Потоковый колбэк ещё не означает потоковую обработку документа. Наш JSON парсер строит объект в памяти, поэтому важно ограничивать размер входа. При нескольких одновременных задачах учитывайте общий пик. Избегайте глобальных изменяемых коллекций, которые разделяются между вызовами скрипта и теряются при рестарте. В production отдельно классифицируйте ошибку данных, отказ инфраструктуры и ошибку кода. Учебный обработчик отправляет проблемы разбора в файл ошибок. После переполнения диска или аварии зависимостей оператору нужна другая реакция и сохранённый контекст.

## Проверки на четырёх входах
- Валидный ID со внешними пробелами
- Пустая строка и отсутствующий ID
- Число вместо строки
- Повреждённый синтаксис JSON
> Перед изменением скрипта выпишите ожидаемое поведение по четырём входам. Для валидного заказа сравните нормализованный результат и убедитесь, что другие поля сохранились. Для остальных зафиксируйте отношение фейльюр и код. Один удачный прогон мало говорит о том, что произойдёт после смены формата. Сохраните примеры как маленький набор входов для будущих изменений. В конце опишите, какой контракт проверяет валидатор данных до скрипта и какие проверки ещё должны оставаться внутри самого правила.
