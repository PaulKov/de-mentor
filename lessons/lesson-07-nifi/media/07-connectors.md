# REST, SOAP, FTP, SMB и JDBC

## REST и маршрут ответа
- InvokeHTTP отделяет request от response
- Код статуса влияет на relationship
- 429 требует отдельного решения
> Откройте описание OpenAPI и найдите операцию получения заказов.
> В процессоре InvokeHTTP укажите адрес сервиса внутри сети стенда и метод GET.
> Найдите, где в потоке оказался исходный запрос, а где тело ответа.
> Код 400 указывает на проблему запроса. Повтор с теми же данными обычно бесполезен.
> Для ответа 429 проверьте заголовок Retry-After и ограничьте число попыток.
> Код 503 может означать временную недоступность сервиса.
> Даже при статусе 200 проверьте, соответствует ли документ схеме заказа.

## SOAP и WSDL
- WSDL описывает operation и binding
- SOAPAction и Content-Type зависят от binding
- Fault читается внутри Envelope
> Откройте файл описания сервиса, WSDL. Найдите в нём операцию GetOrder.
> В примере используется SOAP 1.1. Заголовок SOAPAction указывает действие.
> Его значение возьмите из описания операции. Подставьте XML запроса из стенда.
> После вызова найдите идентификатор заказа внутри тела ответа.
> Затем запросите ошибку и проверьте, есть ли в теле элемент Fault.
> Учебный сервис позволяет сравнить одну ошибку при разных статусах транспорта.
> Если ответ потерялся, установите результат операции до повторной отправки.

## Листинг и загрузка файлов
- ListFTP и ListSmb обнаруживают файлы
- FetchFTP и FetchSmb читают байты
- Готовность файла определяется договором с отправителем
> При получении файла есть два разных момента. Сначала обнаружение, затем чтение.
> ListFTP перечисляет доступные файлы, а FetchFTP получает байты выбранного файла.
> Между этими действиями отправитель может продолжать запись или удалить файл.
> Согласуйте признак готовности, например публикацию под окончательным именем.
> Для FTP проверьте канал передачи данных отдельно от управляющего соединения.
> Для SMB проверьте имя общей папки и доступ к самому файлу.
> Сравните размер и контрольную сумму с проверенным образцом.

## JDBC и инкрементальная выгрузка
- JDBC driver и pool задаются в Controller Service
- Record-операции сокращают число отдельных запросов
- Курсор обновляется по согласованной границе
```sql
WHERE (updated_at, id) > (?, ?)
ORDER BY updated_at, id
```
> Подключение к базе через JDBC задаётся в общем сервисе соединений.
> Представьте две строки с одной отметкой времени. Первая страница вмещает одну.
> Если курсор хранит только время, запрос следующей страницы пропустит вторую.
> На слайде вместе с временем сохраняют ключ и сортируют по обоим полям.
> Ключ должен однозначно разрешать совпадения времени.
> Поздно зафиксированная строка со старой отметкой всё ещё может потеряться.
> Проверьте окно повторного чтения с дедупликацией или чтение журнала изменений.
> Сохранение курсора привяжите к успешной записи выбранной порции.

## Единый контракт ingestion
- Корреляция показывает происхождение заказа
- Политика retry зависит от типа операции
- Карантин сохраняет диагностику и условия replay
> Выберите координаты, по которым сможете заново найти каждый заказ.
> Для файла подойдут путь и версия. Для запроса — адрес, параметры и курсор.
> Для Kafka запишите топик, раздел и смещение прочитанного сообщения.
> При помещении в карантин сохраните эти координаты и версию преобразования.
> Теперь остановите один источник и подайте повреждённый документ через другой.
> Как показать, что произошли два независимых сбоя?
> Сопоставьте время, компонент и причину для каждого из двух заказов.
