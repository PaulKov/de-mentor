# JOLT и маршрутизация JSON

## Контракт преобразования
- Вход содержит order.customer и order.lines
- Выход содержит event_id и items
- У повторяющихся строк сохраняются индексы
> Сначала опишем желаемый результат на двух заказах. У первого есть клиент и две позиции. У второго клиента нет и список позиций пуст. Внешний формат заказа вложенный, а далее нам нужен стабильный плоский идентификатор с массивом итемс. JOLT применяет описание преобразования к дереву JSON. Мы отдельно зададим перенос полей и значения по умолчанию. Если сначала написать длинный шаблон и проверить его только на одном входе, ошибка индекса часто выглядит правдоподобно. Поэтому оба заказа из примера необходимы для проверки.

## JOLT-спецификация
- shift переносит поля по путям
- Звёздочка проходит по элементам
- &N обращается к совпадению на уровне дерева
- default добавляет отсутствующие значения
```text
order.id             => event_id
order.lines[*].sku   => items[*].sku
order.lines[*].qty   => items[*].quantity
```
> В режиме чейн операции выполняются по очереди. Шифт описывает соответствие между входными и выходными путями. На верхнем уровне звёздочка проходит по заказам, а внутри лайнс другая звёздочка проходит по позициям. Выражение амперсанд с числом обращается к совпадению выше по дереву. Для поля товара нужно сохранить одновременно индекс заказа и индекс позиции. В готовом файле проверьте их отдельно. После шифт стадия дефолт заполняет пустой массив там, где его требует выходной контракт. Проверка количества и состава элементов помогает поймать склейку заказов.

## Null, массивы и типы
- Ноль, одна и две позиции дают согласованную форму
- null и отсутствующее поле проверяются отдельно
- Типы валидируются по контракту
> Если входная система иногда отдаёт объект вместо массива, заранее решите, разрешена ли такая форма. В одном проекте инженер приводит одиночный объект к массиву. В другом это нарушение схемы и причина отклонить запись. Аналогично с количеством в виде строки. Правило переноса само по себе не гарантирует корректное число и диапазон. На маленьких примерах можно построить таблицу входов и ожидаемых выходов. Добавьте проверки нулевого количества, пропущенного SKU и чужого поля, которое по контракту нельзя переносить дальше.

## Ошибки, retry и quarantine
- Невалидный JSON идёт в failure
- Ошибка контракта получает код и источник
- Retry имеет лимит и интервал
> Ошибка синтаксиса JSON требует другого действия, чем временная недоступность базы. Повтор исходных повреждённых байтов обычно не улучшает результат. Сохраним такой флоу файл в карантине с причиной и координатой источника. Для временного отказа выберем ограниченный повтор, задержку и конечный исход. В нашем готовом графе ошибка базы также сохраняется для анализа. В воркбуке есть упражнение, где вам предстоит добавить раздельные ветки. Проверьте, что ошибка записи самого карантина остаётся видимой в очереди или алерте.

## Память и масштаб
- JOLT строит дерево входного JSON в памяти
- Большой пакет ограничиваем до трансформации
- Проверяем объём, конкуренцию и время обработки
> JOLT хорошо подходит для структурной перекладки небольших JSON документов. Внутри трансформация работает с деревом и может потребовать гораздо больше памяти, чем размер исходного текста. Если увеличить размер входа и параллельность одновременно, риск вырастет с обеих сторон. Зафиксируйте объём на документ и допустимое число одновременных задач. Для больших входов рассмотрите поштучный контракт, разделение пакета или преобразование через Record API. Определите критерий, при котором ваше решение перестаёт укладываться в бюджет памяти и задержки.
