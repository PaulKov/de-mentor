# Первый dataflow в Apache NiFi

## Задача интеграции
- Источник отдаёт заказ
- NiFi принимает, преобразует и направляет
- Получатель фиксирует результат
> Представьте, что магазин присылает заказ, а бухгалтерия ждёт строку в базе.
> Заказ уже отправлен. Как узнать, где он сейчас?
> В Apache NiFi маршрут данных виден на рабочем полотне.
> Один блок принимает заказ, второй меняет поля, третий отправляет результат.
> Соединения между блоками позволяют увидеть, где заказ ждёт обработки.
> Сегодня проследим один заказ от генератора до записи в PostgreSQL.
> Для этого понадобятся номер заказа и история его движения.

## FlowFile и атрибуты
- Content содержит байты, например JSON
- Attributes содержат строки, например filename
- Provenance связывает шаги обработки
> Единица работы в NiFi называется FlowFile.
> В нашем примере содержимое FlowFile — байты документа JSON.
> Отдельно хранятся строковые атрибуты, например имя файла или адрес источника.
> Откройте один объект в очереди и сравните вкладки атрибутов и содержимого.
> Что изменится, если дать файлу другое имя?
> Изменится атрибут filename. Байты заказа останутся прежними.
> А в Data Provenance можно проследить, какой процессор изменил этот объект.

## Узлы на полотне
- Processor выполняет операцию
- Relationship описывает исход
- Connection хранит очередь FlowFiles
- Process Group задаёт границу группы
> На рабочем полотне каждый процессор выполняет одну операцию.
> Исход операции называют relationship. Например, success означает успех.
> Чтобы передать результат дальше, соедините этот выход со следующим процессором.
> Соединение содержит очередь. Заказ может подождать здесь, пока база занята.
> У ошибки может быть собственная ветка для разбора исходного документа.
> Несколько процессоров удобно объединить в Process Group.
> Откройте группу двойным щелчком и проследите одну ветку целиком.

## Демонстрация в Docker
- Группа Lab 01 · Kafka and PostgreSQL
- Run Once на генераторе заказов
- Queue и Data Provenance
> В первой лабораторной откройте группу с Kafka и PostgreSQL.
> Запустите обработчики, а у генератора заказов выберите Run Once.
> Генератор один раз выпустит документ с двумя учебными заказами.
> Найдите его в Data Provenance по времени запуска и имени компонента.
> Проследите преобразование, публикацию в Kafka и чтение из топика.
> Последний процессор записывает разобранные заказы в таблицу.
> Проверьте оба идентификатора запросом из воркбука.

## Практика с очередью
- Остановленный sink удерживает вход в очереди
- Возобновление sink освобождает очередь
- SQL подтверждает, что результат записан
> Теперь остановите только процессор записи в базу и повторите отправку.
> Посмотрите на число объектов и объём очереди перед этим процессором.
> Что должно случиться с уже полученными заказами?
> Они дождутся возобновления записи, если срок хранения в очереди не истёк.
> Запустите процессор и дождитесь, пока очередь опустеет.
> Сверьте строки в базе по идентификаторам и посмотрите историю каждого заказа.
> Так можно отличить доставку документа от фиксации результата в базе.
