# Первый dataflow в Apache NiFi

## Задача интеграции
- Источник отдаёт заказ
- NiFi принимает, преобразует и направляет
- Получатель фиксирует результат
> Представим, что магазин отдаёт заказы в виде файлов, а аналитическая система ждёт сообщения в брокере. Нужно забрать файл, проверить поля, привести порядок и формат данных к контракту и доставить результат. При сбое важно понять, что уже было обработано. Apache NiFi позволяет собрать эту цепочку из процессоров. Каждый процессор выполняет ограниченную операцию, например читает файл или публикует сообщение. На полотне между шагами видны очереди. Начнём с одного небольшого заказа и сразу посмотрим, где его искать после каждого шага.

## FlowFile и атрибуты
- Content содержит байты, например JSON
- Attributes содержат строки, например filename
- Provenance связывает шаги обработки
> Объект, который движется по полотну, называется флоу файл. Представьте, что у него есть содержимое и карточка с метаданными. В содержимом лежат байты. Карточка содержит имя файла, тип данных и другие строковые атрибуты. Если разбираем JSON и хотим маршрутизировать по номеру заказа, процессор может вынести номер в атрибут. Сам документ при этом остаётся в содержимом. Идентификатор флоу файла помогает искать события в Найфай. Для распознавания повторной бизнес операции лучше использовать идентификатор самого заказа или события из контракта.

## Узлы на полотне
- Processor выполняет операцию
- Relationship описывает исход
- Connection хранит очередь FlowFiles
- Process Group задаёт границу группы
> Процессор имеет свойства, расписание и именованные исходы. После успешного разбора флоу файл идёт по связи саксэсс, а некорректный вход может уйти в фейльюр. Соединение воплощает эту связь в виде очереди, которую можно открыть из интерфейса. Группа процессов объединяет связанный набор шагов. В ней можно разместить общие сервисы, например поток подключений к базе, чтобы несколько процессоров пользовались одной конфигурацией. Группу удобно рассматривать как отдельную интеграцию с именем, входом, выходом и владельцем.

## Демонстрация в Docker
- Группа Lab 01 · Kafka and PostgreSQL
- Run Once на генераторе заказов
- Queue и Data Provenance
> Откройте ссылку на Найфай из воркбука и войдите с учебными реквизитами. В корне откройте группу с Кафкой и Постгресом. Найдите генератор заказов в верхней части. Выберите запуск один раз. Остальные процессоры в готовом потоке продолжают работу самостоятельно. Включите показ данных о происхождении для генератора. В событиях виден идентификатор и объём. Проследите цепочку до публикации. Если очередь успела опустеть, это ожидаемо при быстрых downstream процессорах. События провенанс помогают найти уже прошедший документ.

## Практика с очередью
- Остановленный sink удерживает вход в очереди
- Возобновление sink освобождает очередь
- SQL подтверждает, что результат записан
> Остановите процессор записи в базу, сохранив работающий Kafka consumer. Запустите генератор один раз. Верхняя ветка отправит сообщение, а нижняя получит его и положит в очередь перед базой. Откройте список флоу файлов, отметьте размер и проверьте содержимое. После запуска записи очередь должна опустеть. Для последней проверки выполните запрос из воркбука. Зафиксируйте количество строк и названия полей. Так мы отдельно увидели, что источник работал, данные дошли до очереди, а внешний результат действительно появился.
