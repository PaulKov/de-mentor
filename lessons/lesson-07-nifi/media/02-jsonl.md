# JSON, JSONL и Record API

## Фрейминг JSON и JSONL
- JSON-документ может содержать массив
- JSONL содержит отдельное значение JSON на каждой строке
- Пустая строка не является JSON-записью
```json
{"event_id":"o-101","qty":2}
{"event_id":"o-102","qty":1}
```
> В обычном JSON документе два заказа удобно положить внутрь массива. Парсер получает один массив как целое. В формате джейсон эл разделителем записей служит перевод строки. Каждая строка является самостоятельным JSON значением. В нашей интеграции контракт дополнительно требует объект заказа. Расширение файла само по себе не подтверждает формат. Красивый многострочный объект можно прочитать как JSON, но он нарушит контракт джейсон эл. Пустая строка тоже не является записью. Кодировка, наличие конечного перевода строки и допустимый размер строки входят в договорённость источника с потребителем.

## FlowFile, Record и Kafka message
- FlowFile содержит исходные байты
- Record Reader выделяет отдельные записи
- Kafka message определяется настройками публикации
> Один флоу файл может хранить целый массив или файл на тысячу строк. Рекорд ридер выделяет структурные записи по правилам формата. Рекорд райтер кодирует их снова. Kafka message представляет другую единицу. В нашем стартовом варианте один файл с двумя заказами публикуется одним сообщением. Если включить обработку записей с читателем и писателем, можно передавать заказ отдельным сообщением и выбирать ему ключ. Перед настройкой полезно записать три ожидаемых счётчика. Это число полученных файлов, число заказов и число сообщений брокера.

## Явная схема и смысл полей
- id хранит идентичность в текстовом виде
- decimal сохраняет согласованную точность
- absent, null и пустая строка имеют разный смысл
> Рассмотрим поле ай ди со значением ноль ноль сорок два. Если превратить его в число, потеряются два знака, которые могут быть частью внешнего идентификатора. Для денег определим точность и масштаб с помощью decimal либо целых копеек. Далее уточним смысл отсутствующего поля. Например, отсутствие клиента может означать «источник его не прислал», а явное налл — «источник его удалил». При автоматическом выводе схемы один такой пример может дать неожиданный тип. На границе интеграции фиксируйте схему и проверяйте совместимость на примерах разных версий.

## Повреждённая строка в середине файла
- Одно правило для всего файла или карантин по строкам
- Сохраняем имя файла, номер строки и код ошибки
- Проверяем обработку записей после ошибки
> Файл содержит правильный заказ, сломанную вторую строку и правильный третий заказ. Есть два осмысленных договора. Если файл представляет атомарный пакет, при ошибке отклоняем весь файл и сохраняем исходник. Если каждая строка независима, валидные записи могут пройти, а сломанная строка уйдёт в карантин. Во втором случае обязательно сохраните её координату. Проверьте, умеет ли выбранный reader продолжить чтение после ошибки. Если процессор завершается на первой ошибке, нужна отдельная стадия разбиения или другой режим парсинга. Используйте fixture из воркбука и измерьте результат.

## Задание на доказательство
- Валидный JSONL даёт две записи
- Ошибка framing отмечается отдельно от ошибки схемы
- Повтор файла сохраняет идентичность заказов
> Подайте валидный образец джейсон эл и сохраните наблюдаемый результат. Затем используйте образец с повреждённой серединой и объясните, что произошло с каждой строкой. Добавьте объект с пустым ай ди. Он разбирается как JSON, но нарушает бизнес контракт. Это другой класс ошибки. Наконец, повторите подачу того же файла. Предскажите число новых флоу файлов и бизнес строк после повтора. Такая проверка показывает, где обеспечивается уникальность и какая статистика относится только к обработке транспорта.
