# JSON, JSONL и Record API

## Фрейминг JSON и JSONL
- JSON-документ может содержать массив
- JSONL содержит отдельное значение JSON на каждой строке
- Пустая строка не является JSON-записью
```json
{"event_id":"o-101","qty":2}
{"event_id":"o-102","qty":1}
```
> Первый пример — массив JSON. Весь массив составляет одно значение.
> Теперь посмотрите на две строки кода. Это формат JSON Lines, сокращённо JSONL.
> Каждая строка содержит одно значение JSON. Здесь это объект заказа.
> Число и значение null тоже допустимы. Пустая строка нарушает формат.
> Контракт нашего получателя строже. Он принимает только объекты заказов.
> Файл в кодировке UTF-8 можно читать последовательно, строку за строкой.
> Перенос строки внутри красиво оформленного объекта нарушит границу записи.
> Внутри строки JSON перевод строки в тексте поля записывается через экранирование.

## FlowFile, Record и Kafka message
- FlowFile содержит исходные байты
- Record Reader выделяет отдельные записи
- Kafka message определяется настройками публикации
> Сколько заказов в одном FlowFile? Это зависит от его содержимого.
> Один FlowFile может нести целый файл с тысячей строк.
> Record Reader читает байты по правилам формата и выделяет записи.
> Схема подсказывает, как интерпретировать типы полей каждой записи.
> А сколько сообщений получит Kafka? Это уже настройка публикации.
> В стенде один массив уходит одним сообщением, а в базе появляются две строки.
> При сверке отдельно посчитайте файлы, сообщения и записи.

## Явная схема и смысл полей
- id хранит идентичность в текстовом виде
- decimal сохраняет согласованную точность
- absent, null и пустая строка имеют разный смысл
> У заказа номер с ведущими нулями. Что произойдёт при переводе в число?
> Нули исчезнут, и два разных текстовых ключа могут совпасть.
> Задайте идентификатору строковый тип, а денежной сумме — десятичный.
> Для суммы согласуйте точность, допустимое округление и валюту.
> Если поля клиента нет, источник мог вовсе не передавать сведения.
> Явное значение null может означать, что связь с клиентом снята.
> Запишите смысл каждого случая в контракте и добавьте отдельный пример.

## Повреждённая строка в середине файла
- Одно правило для всего файла или карантин по строкам
- Сохраняем имя файла, номер строки и код ошибки
- Проверяем обработку записей после ошибки
> В файле с ошибкой первая строка верна, вторая оборвана, третья снова верна.
> Должна ли третья строка попасть в базу?
> Если файл принимают целиком, ошибка отклонит всю поставку.
> Если строки независимы, сохраните вторую в карантин вместе с номером строки.
> Проверьте, продолжает ли выбранный компонент чтение после ошибки разбора.
> Для изоляции ошибок можно сначала разделить вход по границам строк.
> Сверьте обе корректные записи и возможность найти исходный файл.

## Задание на доказательство
- Валидный JSONL даёт две записи
- Ошибка framing отмечается отдельно от ошибки схемы
- Повтор файла сохраняет идентичность заказов
> Начните с исправного JSONL. В образце две строки и два заказа.
> Затем подайте файл с повреждённой серединой и запишите судьбу каждой строки.
> Теперь передайте объект с пустым идентификатором. Синтаксис JSON здесь верен.
> На какой стадии поток должен отклонить такой заказ?
> Укажите, какое правило схемы или предметной области сработало.
> Наконец, отправьте исходный файл второй раз и сверьте ключи в базе.
> Так вы раздельно проверите границы записей, валидацию и защиту от повторов.
