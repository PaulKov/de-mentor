# Deep Dive · Репозитории NiFi и runtime

## FlowFile Repository и Content Repository
- FlowFile Repository хранит метаданные живых FlowFiles
- Content Repository хранит содержимое и claims
- Очереди восстанавливаются по сохранённому состоянию
> После чтения сообщения Найфай записывает его содержимое в контент репозиторий. Флоу файл хранит ссылку на область содержимого и метаданные. Очередь относится к активному состоянию обработки. Флоу файл репозиторий сохраняет это состояние и изменения, чтобы поддержать восстановление. Когда мы меняем только атрибут, копировать байты заказа не требуется. Перезапуск процесса с сохранёнными томами и потеря диска — два разных эксперимента. Первый помогает проверить восстановление. Второй требует оценить, какие журналы и источники позволяют воспроизвести работу.

## ProcessSession и переиспользование контента
- get, write, putAttribute и transfer выполняются в сессии
- Clone может делить неизменившееся содержимое
- После commit состояние доступно downstream
> В сессии процессор получает флоу файл и меняет его. Запись может создавать новый контент, сохраняя ссылку на старую версию там, где она ещё нужна. Клонирование позволяет разделять неизменившиеся байты. После завершения сессии результат оказывается в очереди следующего соединения. Если транзакция сессии откатывается, локальное состояние возвращается в предусмотренное процессором состояние. Внешний эффект может уже существовать. Для временного отказа посмотрите, что конкретный процессор делает с отношением, penalization и повторным планированием. Эти свойства важнее, чем абстрактное слово транзакция.

## Provenance, replay и state
- Provenance показывает цепочку событий
- Replay зависит от сохранности content и topology
- Состояние List-процессора хранится отдельно
> Провенанс отвечает на вопрос, как данные попали в текущую точку. У события есть тип, время, компонент и атрибуты. При наличии разрешений и сохранённого контента можно посмотреть исходные байты или выполнить replay в подходящую точку. Старое событие может остаться в истории после того, как байты уже очищены. Отдельно существует state процессора. Например, листинг помнит файлы или отметку времени, чтобы не забирать всё заново при каждом запуске. Очистка этого state может привести к повторному листингу. Перед любой очисткой зафиксируйте, что уже опубликовано и может быть повторено безопасно.

## Backpressure, penalize и yield
- Backpressure ограничивает очередь по count и bytes
- Penalize задерживает отдельный FlowFile
- Yield временно уменьшает активность процессора
> Пусть база принимает меньше записей, чем приходит от источника. Очередь перед ней растёт. Когда достигнут порог объектов или объёма, Найфай ограничивает работу upstream в соответствии с моделью соединения. Очередь остаётся наблюдаемой и помогает локализовать узкое место. Пеналайз откладывает работу с отдельным флоу файлом, например после временной ошибки. Йилд задерживает процессор. Ни один из этих механизмов сам по себе не задаёт SLA обработки и число попыток. Измеряйте возраст старейшей записи, скорость поступления и время освобождения backlog после восстановления.

## Кластер и эксплуатация диска
- Узел хранит собственные очереди и content
- Primary Node подходит для некоторых заданий сбора
- Persistent volumes и state входят в план восстановления
> В кластере поток и работа процессоров распределены по узлам. Это не означает, что любая очередь автоматически имеет независимую копию на каждом узле. Для источников вроде листинга рассмотрите запуск на первичном узле и согласованность состояния при смене назначения. Для работы с локальными файлами проверьте доступность пути каждому нужному узлу. При эксплуатации отдельно наблюдайте свободное место и время записи репозиториев. Наш одновузловой стенд подходит для проверки рестарта, очередей и состояния. Потерю узла и перераспределение кластерной работы нужно проверять на кластере.
