# Самопроверка после уроков 04, 06 и 10

Ответь своими словами. Для практических вопросов приведи показатель или команду, которую реально проверил.

1. Чем content отличается от attributes? Куда положить идентификатор, нужный для маршрутизации?
2. Откуда NiFi может взять сохранённый FlowFile после рестарта? Где искать историю?
3. В JSONL три строки, средняя повреждена. Как отличаются пакетный и поштучный контракты?
4. Как в JOLT отловить склейку позиций двух заказов?
5. Что изменится, если два потребителя используют один group ID? Что даст другой ID?
6. Log end offset увеличился на четыре, а consumer получил два payload. Что проверить?
7. Почему XPath `/Order/Id` не увидел `<Order xmlns="urn:lab:orders">`?
8. После `session.write` Groovy сохраняет результат в старой переменной. Что исправить?
9. POST получил read timeout. Как решить, допустим ли повтор?
10. Чем отличается реакция на HTTP 400, 429, 503 и SOAP Fault с HTTP 200?
11. База приняла commit, NiFi повторил событие. Какие данные нужны для безопасного повтора?
12. Kafka lag=0, PostgreSQL не обновляется. Назови первые проверки по порядку.

<details>
<summary>Ключ для сверки</summary>

1. Content содержит байты, attributes — строковые метаданные. Короткий ID можно продублировать в атрибут для маршрута, сохранив бизнес-идентичность в payload.
2. Активное состояние очереди восстанавливается из FlowFile Repository, байты читаются из Content Repository. История доступна в Provenance Repository при соответствующем retention.
3. Пакетный договор отклоняет весь вход. Поштучный может принять строки 1 и 3 и сохраняет номер и причину строки 2.
4. Подать минимум два заказа с отличающимися позициями, проверить исходные индексы и массив каждого по порядку.
5. Одна группа делит partitions, другая читает журнал независимо со своей позицией.
6. Проверить transaction markers и режим чтения, затем данные конкретной partition.
7. XPath 1.0 без префикса ищет элементы без namespace. Связать `o` с URI и использовать `/o:Order/o:Id`.
8. Сохранить возвращённую ссылку на FlowFile после записи контента или изменения атрибутов.
9. Посмотреть idempotency key, внешний статус и контракт. При неопределённом результате слепой повтор может удвоить эффект.
10. 400 требует исправления входа, 429 ждёт Retry-After, 503 допускает ограниченный retry, SOAP Fault классифицируется по телу и бизнес-контракту.
11. Стабильный ID, SQL uniqueness, политика сравнения hash и атомарность применения бизнес-эффекта. Для версий — монотонная проверка в той же транзакционной границе.
12. Сначала source и LEO, потом Kafka → NiFi по queue/provenance, затем failure и SQL в нужной БД.
