# Итоговый проект · Доставка синтетических заказов

Собери свою Process Group с двумя источниками. Первый отдаёт JSONL, второй — XML с namespace. Получатель читает стандартизированное событие из Kafka и хранит актуальные строки в PostgreSQL. Исходники стенда и контрактов уже в [labs/nifi](../../labs/nifi/README.md).

## Контракт

- Выходные поля `event_id`, `order_id`, `source_version`, `items`, `origin`. Идентификатор стабилен при повторе. Для Kafka key используй `order_id` и опиши, какое упорядочивание требуется.
- Для XML валидируй URI namespace, порядок несущественных полей и повторяемые позиции. Для JSONL реши, можно ли принять валидные строки частично, и сохрани координаты битой строки.
- Записи с одинаковым `event_id` и теми же данными совместимы с повтором. При том же ID и конфликтующем payload сохрани отдельное наблюдаемое событие. Для устаревшего обновления сравни версии до записи внешнего эффекта.

## Реализация и доказательства

1. Трансформируй один формат с помощью JOLT и другой с помощью XSLT. Добавь небольшое проверяемое правило на Groovy.
2. Сохрани ошибку формата в карантине и сделай ограниченное число попыток для временного отказа получателя. Проверь ошибку самой ветки карантина.
3. Воспроизведи три инцидента. Останови БД, подай битую среднюю строку JSONL, затем повтори старый заказ после новой версии. По каждому запиши Kafka координаты, видимость dataflow и результат SQL.
4. Задай учебный SLO, например 99% валидных заказов доходят за 30 секунд при согласованном входе. Сравни нормальный прогон, остановку и время разгрузки backlog. Измерь несколько серий и сохрани условия.
5. Экспортируй свою группу как JSON. Укажи параметры, команды повторного прогона и стратегию безопасного восстановления. Выходные артефакты должны использовать только синтетические данные.
