# Principal Engineer capstone — миграция пакетного источника на Redpanda → Flink → Iceberg

Вымышленный интернет-магазин отправляет выгрузки заказов. Старый потребитель читает их из имитатора хранилища, новый получает те же данные через Redpanda. Все записи, размеры и SLO ниже синтетические. Реализуй mock генератор и эталонный reader, который вычисляет ожидаемый результат независимо от Flink. Используй открытые компоненты. [Учебный стенд Flink и Iceberg](../../../labs/flink-iceberg/README.md) показывает запись через Kafka API с брокером Apache Kafka. Для приёмки Redpanda используй сам Redpanda, его listeners и настройки доступа. [Совместимость Redpanda с Kafka-клиентами](https://docs.redpanda.com/streaming/current/develop/kafka-clients/) · [Настройка listeners Redpanda](https://docs.redpanda.com/streaming/current/manage/security/listener-configuration/)

## 1. Спроектируй контракт и докажи инварианты

| Поток | Вход и выход | Инвариант |
| --- | --- | --- |
| `orders_snapshot` | Версионированная полная выгрузка для `scope=region`. Эталонное состояние содержит последний опубликованный полный набор для каждого региона | Читатель видит одну целую версию региона. Отсутствующая в новой выгрузке строка исчезает только в её регионе. Задержавшаяся старая версия не заменяет новую |
| `payments_append` | Неизменяемые события. У события есть уникальный в рамках потока `event_id` и версия схемы | Повтор того же события не меняет результат. Одинаковый ID с разным содержимым вызывает расследование по заданной политике |

Минимум для `orders_snapshot`: `stream`, `scope`, неизменяемый `batch_id`, монотонный `source_sequence` в пределах scope, `package_index` от 1 до N, `schema_version` и массив строк. Отдельный manifest содержит те же идентификаторы, N, ожидаемый row count и digest каждого пакета. Зафиксируй кодировку и канонизацию digest. Сохраняй `topic/partition/offset` как координаты приёма. Идентификатор пакета и координаты Kafka имеют разный жизненный цикл.

| Порядок входа | Содержимое | Что должен увидеть читатель |
| --- | --- | --- |
| `north/41` manifest, пакет 2, дубликат пакета 2, пакет 1 | Пакет 1 содержит `o-1=10.00`, пакет 2 — `o-2=7.00` | До пакета 1 предыдущая версия. После проверки `41`: два заказа, сумма 17.00 |
| `north/42` manifest, пакет 1 из 2 | Пакет 1 содержит `o-2=8.00` | По-прежнему `41`, отдельный сигнал о неполном batch |
| `north/42` пакет 2 | Пустой пакет, явно указанный в manifest | После проверки `42`: только `o-2`, сумма 8.00 |
| `north/41` повтор целого batch после `42` | Все байты идентичны первому приёму | По-прежнему `42` |
| `south/3` полный batch из одного пакета | `o-3=12.00` | `south/3` доступен параллельно с `north/42` |
| `north/43` валидный manifest без пакетов | Явно объявлены ноль строк, ноль пакетов и пустая полная выгрузка | После публикации `north` пуст. `south` остаётся без изменений |

Воспроизведи эти последовательности при разных partition layouts. Manifest может прийти первым. Порядок Kafka сохраняется внутри partition, поэтому merge после чтения нескольких partitions должен работать при любой допустимой перестановке. Верификатор должен сверять набор номеров, согласованность заголовков, digest, count и уникальность ключей в scope до публикации.

## 2. Реализуй и объясни путь публикации

1. Сгенерируй байты в Python. Эталон читает те же выгрузки независимо и выдаёт отсортированные ключи, канонические контрольные суммы и бизнес-агрегаты по версиям.
2. Во Flink реализуй разбор envelope, контроль версий, keyed state по `(stream, scope, batch_id)`, таймер для неполного batch и отвод ошибок с причиной. Храни крупные payload в staging, если хранение всех байтов в state нарушит checkpoint SLO. Докажи предел state и поведение после истечения TTL.
3. Зафиксируй сырые данные, результаты проверок и версию схемы в Bronze. Публикуй полные выгрузки атомарно в границах выбранного scope. Один вариант — bounded Iceberg commit с явной заменой области таблицы. Другой — immutable versioned data плюс указатель, который читатель обязан учитывать. Для указателя спроектируй проверку видимости staging snapshot, защиту от гонок и восстановление между коммитами. Проверь пустую выгрузку отдельно: динамическая замена затронутых partitions может не удалить scope, если во входе вообще нет строк.
4. Объясни, кто и где применяет fencing по `source_sequence`. Для двух издателей смоделируй поздний commit и одновременный повтор. Отдельная проверка версии перед записью не защищает от гонки без общей границы условного обновления или сериализации.
5. Покажи, как обнаружить, что commit прошёл, если ответ потерян. Используй наблюдаемое состояние таблицы и устойчивый идентификатор публикации. Раздели recovery того же Flink job из checkpoint и новое submission с иным состоянием.

Два независимых Iceberg commits требуют явной координации. Например, указатель на staging можно продвинуть только после подтверждения видимости конкретной версии, а интерфейс чтения должен проверять указанный snapshot или идентификатор версии. В Gravitino Iceberg REST 1.3.1 multi-table transactions не реализованы. [Iceberg Flink writes](https://iceberg.apache.org/docs/latest/flink-writes/) · [Gravitino REST capabilities](https://gravitino.apache.org/docs/1.3.1/iceberg-rest-service/)

## 3. Матрица пограничных случаев

Для каждого случая укажи триггер, ожидаемый инвариант, сигнал для оператора и безопасное действие. В колонке фактов отдельно отмечай, что воспроизвёл, а что проверил на уровне модели.

| Слой | Пограничный случай | Доказательство или реакция |
| --- | --- | --- |
| Источник | Producer повторяет тот же пакет с новым Kafka offset | Одна логическая версия. Сравни digest и ID, сохрани оба входных offset |
| Источник | Тот же package ID, другой digest или изменённый `package_total` | Останови публикацию этой версии, зафиксируй конфликт |
| Источник | Manifest первым, потерянный пакет, задержка дольше state TTL | Никакой частичной публикации. Поздний пакет либо восстанавливает batch из durable staging, либо открывает управляемый повтор |
| Источник | Повтор старого batch после продвижения более новой версии | Метрика stale/replay. Видимая версия монотонна по scope |
| Источник | Пустой snapshot и корректировка, пришедшая во время переключения | Пустой scope заменяет старый только при валидном manifest. Определи порядок correction, replay и cutover |
| Redpanda | Запись превышает лимит сообщения | Отказ наблюдаем. Для ссылок на объект проверь checksum, завершённость upload и отдельную retention policy для объекта |
| Redpanda | Изменение числа partitions, лидер недоступен, broker адрес недостижим | Восстановление маршрута и повтор приёма не меняют контракт группировки. Отдельно измеряй отсутствие прогресса и рост lag |
| Redpanda | Сохранённый offset выходит за retention после долгого простоя | Явный сигнал об утрате диапазона. Восстанови из архивной выгрузки либо объяви нарушение RPO |
| Flink | Сбой до/после checkpoint, checkpoint завершён до Iceberg commit | Сравни восстановленный checkpoint, прочитанные offsets и реально опубликованный snapshot |
| Flink | Rescale или обновление serializer после savepoint | Проверь UID и совместимость состояния, пометь несовместимое обновление до допуска на production |
| Flink | Idle partition, timestamp из будущего, skew или рост state | Отдельно измерь watermark, backlog и checkpoint age. Не используй watermark как доказательство полноты batch |
| Схема | Rename, добавление optional поля, смена precision или повторное использование имени | Сверь field IDs, политику совместимости и сумму DECIMAL; неподдерживаемый пакет отправь на разбор |
| Iceberg | Таймаут после отправки commit, конкурентный rewrite/overwrite | Отличи неизвестный результат от отказа. Проверь целевую версию и метаданные прежде, чем повторять |
| Каталог | Потеря HTTP/API, потеря metadata DB, stale cache, запись через другой API | Раздели недоступность указателя, rollback backend и видимость reader. Докажи общий авторитет записи |
| Storage | Истёк токен в середине работы или потерян объект активного snapshot | Различи auth и data loss. Восстанови затронутые объекты и проверь чтение snapshot вторым движком |
| Maintenance | Compaction, expiration или orphan cleanup пересекаются с recovery | Покажи retention запас для активных writers и восстановление после повторного коммита |
| Миграция | Две доставки, backfill параллельно live, частичный cutover | Сверь одни и те же ID и контрольные суммы в обоих контурах. Сохрани рубеж по scope и правило rollback |

## 4. Измерь и защити решение

- **SLO упражнения.** 99% полных batch видны не позже пяти минут после приёма последнего необходимого пакета и manifest. Неполный batch обнаружен за десять минут от первого пакета или manifest. RTO процесса после одиночного сбоя — двадцать минут. Для принятых полных выгрузок целевой RPO равен нулю в явно перечисленных сценариях и окне replay. Опиши отдельный SLI от планового времени выгрузки до видимости.
- **Capacity.** При 5 GiB за 30 минут средний вход около 2.84 MiB/s. Чтобы за 20 минут разобрать 10 GiB backlog при том же входе, нужен минимум 11.38 MiB/s устойчивой обработки. С коэффициентом запаса 1.5 это около 17.1 MiB/s. Замерь отдельно пики и skew, write amplification, размеры файлов, checkpoint I/O и пропускную способность каталога.
- **Выбор каталога.** Напиши ADR с HMS, Lakekeeper, Nessie и Gravitino. Для целевого AWS сценария включи Glue. Проверь REST и FileIO на конкретных версиях двух движков, конфликт двух writers, credential rotation и восстановление backend. [Таблица выбора каталогов](../../lesson-05/docs/catalog-decision-matrix.md)
- **Cutover.** Задай одну точку публикации для потребителей, условия перехода по scope, high-water mark и действия владельца при расхождении. Покажи rollback чтения при сохранённом shadow потоке и отдельно сценарий, когда уже записанные изменения надо вернуть в старую систему.
- **Приёмка.** Приложи команды, версии, логи и временную шкалу. Привяжи один путь от ID выгрузки через Kafka offsets и Flink checkpoint к опубликованному Iceberg snapshot. Параллельный прогон сверяй по ключам, digest и агрегатам. Если данных мало, явно укажи, чего этот прогон не доказывает.

## Проходной критерий

| Область | Баллы |
| --- | ---: |
| Формальный контракт и воспроизводимый эталон | 20 |
| Публикация, idempotency, полнота и граница атомарности | 25 |
| Сбои, наблюдения, replay и восстановление | 25 |
| Выбор каталога, storage, capacity и SLO | 20 |
| Cutover, rollback и защита решений | 10 |

Для оценки Principal Engineer нужно 90 из 100 и наблюдаемые доказательства всех обязательных сценариев: неполная и пустая выгрузки, повтор после новой версии, восстановление Flink, неизвестный результат commit, отказ каталога и откат переключения. На защите студент объясняет, где заканчивается каждая гарантия и какой эксперимент может опровергнуть его вывод. Архитектурные гипотезы помечаются отдельно от измерений.
