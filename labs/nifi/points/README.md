# Практика 09. Одно начисление при повторной доставке

Покупателю начисляют 100 баллов. База уже ответила на `COMMIT`, а процессор записи ещё обрабатывает FlowFile. Что будет, если в этот момент завершить NiFi сигналом `SIGKILL`? В конце опыта у тебя будут четыре попытки обработки, одна запись о принятом событии и два баланса для сравнения.

## Запуск

Нужны Docker с Linux-контейнерами, Python 3 и свободный порт 28444. Из корня репозитория выполни:

```sh
cd labs/nifi
python points_lab.py --report points-run.json
```

Сценарий поднимет Kafka и PostgreSQL основного стенда и отдельный NiFi для аварий на порту 28444. Основное учебное полотно доступно на порту 28443, если его сервис запущен. Для каждого опыта создаются новый счёт, событие, однопартиционный топик, consumer group и группа процессоров. Сценарий печатает ссылку на созданную группу. Вход в отдельный NiFi такой же, как в [основном стенде](../README.md). Один экземпляр аварийного NiFi обслуживает один опыт за раз.

## Сначала предскажи результат

1. После успешного коммита в БД что увидит оператор при `LAG=0`?
2. Совпадёт ли UUID FlowFile после восстановления очереди NiFi? А после повторного чтения самого топика?
3. Что произойдёт при повторной публикации того же события, если для защиты использовать только смещение Kafka?

## Где разрывается обработка

`ConsumeKafka` читает одно сообщение и передаёт FlowFile в очередь. Включён `Commit Offsets=true`. Потребитель подтверждает свою позицию после успешной фиксации сессии приёма. В следующем процессоре [скрипт начисления](apply.groovy) открывает JDBC-транзакцию, вызывает [функцию PostgreSQL](schema.sql) и делает `db.commit()`. Для первого принятого события в учебном режиме затем выполняется отдельный `pg_sleep(180)` перед `session.transfer`.

Сценарий находит в `pg_stat_activity` именно этот ожидающий запрос по идентификатору текущего события, видит в независимом SQL-сеансе зафиксированные 100 баллов и проверяет позицию группы у брокера. После этого он завершает только контейнер `nifi-points`, проверяет код выхода 137, снимает показания при выключенном NiFi и запускает тот же контейнер с прежними томами. Пауза служит воспроизводимой точкой сбоя; в рабочем обработчике она не нужна.

## Ожидаемые показания

Исходное сообщение имеет offset 0 в разделе 0. В колонке Kafka указаны сохранённая следующая позиция группы, конец журнала и отставание.

| Момент | CURRENT / END / LAG | Завершённых попыток в БД | Защищённый баланс | Контроль без защиты |
| --- | --- | ---: | ---: | ---: |
| БД зафиксировала начисление, обработчик ждёт | 1 / 1 / 0 | 1 | 100 | 100 |
| NiFi завершён сигналом SIGKILL | 1 / 1 / 0 | 1 | 100 | 100 |
| После запуска восстановлен FlowFile | 1 / 1 / 0 | 2 | 100 | 200 |
| Группа остановлена и перемотана к offset 0 | 0 / 1 / 1 | 2 | 100 | 200 |
| Заново прочитана исходная запись Kafka | 1 / 1 / 0 | 3 | 100 | 300 |
| Повторно опубликовано то же бизнес-событие | 2 / 2 / 0 | 4 | 100 | 400 |

Группа заново читает только собственный учебный топик. После восстановления очереди сценарий останавливает `ConsumeKafka`, дожидается пустой группы, выполняет `--reset-offsets --to-offset 0 --execute` и возобновляет чтение. Таким образом, в опыте отдельно наблюдаются повтор из очереди, повтор из Kafka и новая публикация с тем же `event_id`. В конце процессоры этого запуска остановлены, UI и данные остаются доступны.

## Как перепроверить показания

В PowerShell, из `labs/nifi`, используй идентификаторы своего запуска:

```powershell
$r = Get-Content -Raw .\points-run.json | ConvertFrom-Json
docker compose exec -T kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka:29092 --describe --group $r.group
Get-Content -Raw .\points\inspect.sql | docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -v "event_id=$($r.event.event_id)" -U student -d integration
```

В Bash подставь напечатанные значения вместо `GROUP` и `UUID`:

```sh
docker compose exec -T kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka:29092 --describe --group GROUP
docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -v event_id=UUID -U student -d integration < points/inspect.sql
```

После окончания опыта у группы может отображаться `has no active members`. Сохранённая позиция остаётся доступной. Сравни её с историей в отчёте. В журнале попыток ожидаются смещения `0, 0, 0, 1` и решения `applied, duplicate, duplicate, duplicate`. Первые две попытки имеют одинаковый UUID FlowFile. У третьей тот же Kafka offset и новый UUID FlowFile. У четвёртой новый Kafka offset, но тот же бизнес-ключ. [Показания завершённого прогона](observed.json).

## Что обеспечивает однократный эффект

В `points_lab.inbox` первичный ключ — `event_id`. Если вставка удалась, функция прибавляет баллы. Если ключ уже занят, она сверяет счёт и сумму с первым событием. При совпадении решение — `duplicate`, при изменившихся данных — `conflict`. Регистрация события, изменение баланса и запись о попытке входят в одну транзакцию PostgreSQL. Если запись баланса откатится, регистрация события тоже откатится и следующая попытка сможет выполнить начисление. Первичный ключ работает и при одновременном поступлении одного события в два обработчика.

В учебной таблице `control_balances` баланс растёт на 100 при каждом совпадающем запросе, даже когда результат — `duplicate`. Она показывает поведение безусловного `balance = balance + 100`. В таблице `protected_balances` строка счёта обновляется только при первой регистрации события. Бизнес-гарантия опыта — один эффект в PostgreSQL на стабильный `event_id` при сохранности данных и успешной доставке хотя бы одной попытки. Повтор должен принести исходный ID. Для другого законного начисления на тот же счёт нужен новый ID. Срок хранения входящих ключей должен покрывать допустимое окно повторной доставки.
